# Behavior contract (what must not change)

Derived from reading the code on the pre-migration commit. Every ID needs a passing Playwright test (`BC-xx ...`) before Phase 1 starts. "Quirk" items are deliberate parity: keep them even though they look like bugs; list fixes in FOLLOW-UPS.md.

## Data flow (App.js, movie-list)
- BC-04 On first load App requests `GET /3/movie/popular?language=en-US&page=1` and stores the results.
- BC-05 Clicking a header link requests page 1 of that category and REPLACES the list. The `page` counter starts at 2; (2026-11-08, Step 5c, owner decision: the quirk "not reset on category change" is GONE, the counter is reset to 2 when the category changes, see BC-32); "Show More" requests `page=<counter>` then increments, appending to the list.
- BC-06 Movie list is a poster grid (`https://image.tmdb.org/t/p/w500` + `poster_path`); click or Enter on a poster loads `GET /3/movie/{id}` and opens the details dialog.
- BC-07 If a list route has an empty list, it redirects to `/home`.
- BC-08 "Show More" button is visible when the list is non-empty and appends the next page.
- BC-09 Infinite scroll: smooth-scrollbar `onScroll` -> 600 ms debounce -> IntersectionObserver on the last poster (`id = length-1`) -> `append()`. Step 5 (2026-11-08): the observed element is now a zero-height sentinel below the grid (the last poster may be unmounted by windowing); the observer is created once and rooted on the scrollbar viewport, the scroll -> 600 ms debounce trigger is unchanged (a visible sentinel alone never requests a page), and a page is requested once per list growth (BC-25). Details: BC-24..BC-29.
- Note 2026-11-08 (Step 5b, owner decision, SUPERSEDES the trigger above and the earlier owner answer "next-page trigger as before"): the scroll -> 600 ms debounce trigger, rootMargin 0 and "a visible sentinel alone never requests a page" are gone. The next page is prefetched by the sentinel observer 3 viewport heights ahead, without a scroll and without a debounce (BC-31). Everything else here (sentinel instead of the last poster, one observer rooted on the scrollbar viewport, `append`/URLs/page numbering, BC-10) is unchanged.
- BC-10 On mount of a list view at viewport width 768-1024 px the app clicks "Show More" 5 times automatically (and logs "clicked").

## Theme and accessibility (migration/movie-atlas step 3, 2026-11-07)
- BC-19 Light/dark mode. Dark is the default and today's look (header #21252d, mint #64dcb0). A header icon button (sun in dark, moon in light; desktop: after Now Playing; mobile: right end of the bar) switches the mode; its accessible name states the action ("Switch to light mode" / "Switch to dark mode"). The choice is stored in localStorage key `movie-atlas-theme` (reads/writes are guarded: with storage blocked the app works and defaults to dark) and applied as `data-theme` on <html> by an inline script in index.html before first paint. The system prefers-color-scheme is ignored. Light: white header/cards with dark text, accent #0b7a5a; the wallpaper (collection.jpg) is the same image with a rgba(255,255,255,.8) wash. Tokens: src/theme.css. MUI theme is built per mode (src/theme.ts); v4 primary/secondary/breakpoints pins kept (dark), light uses secondary #c51162. Colours: docs/migration/ACCESSIBILITY-COLORS.md. Update 2026-11-08 (owner design change): the light wash is a gradient, `linear-gradient(rgba(255,255,255,0.2), rgba(255,255,255,0.8) 35%)` over the same photo (lighter at the top, flat 0.8 from 35% down), instead of a flat 0.8; light `--card-border` is `#1a1f26`.
- BC-20 Header keyboard navigation. Tab order: Skip to main content link (visible on focus; Enter moves focus to `<main id="main-content" tabindex="-1">` without changing the hash route), Home, Popular, Top Rated, Now Playing, theme toggle, then the page. Every stop shows a >= 2px :focus-visible ring (>= 3:1). Mobile: hamburger (Enter/Space toggles; aria-expanded), theme toggle, menu links only while the menu is open (closed menu is display:none, so not tabbable); Esc closes the menu and focuses the hamburger. Poster tiles, dialog focus handling and the autocomplete are NOT part of this item (later steps).
- BC-21 Contrast: WCAG 2.2 AA (4.5:1 text, 3:1 large text, UI boundaries and focus rings) in both modes for the header, nav states, About cards and links, search heading/input/placeholder/options, poster list, Show More, details dialog and mobile menu. Regression: axe color-contrast on Home, Popular and the open dialog in both modes plus pixel measurements for pairs on the wallpaper (e2e/a11y-contrast.spec.js). Update 2026-11-08: the light wallpaper pixel pairs are measured under the gradient wash (static photo plus the four pan poses, thresholds unchanged: heading >= 3, card border >= 3, input boundary >= 3, input ring >= 3, placeholder >= 4.5); worst case heading 4.99, card border 3.20, input border 3.40, input ring 3.31.

- BC-22 Search autocomplete accessibility (migration/movie-atlas step 4, 2026-11-07), WAI-ARIA APG editable combobox with list autocomplete. `#auto` has role=combobox, aria-autocomplete=list, aria-expanded (true only while the popup shows), aria-controls=movie-search-listbox, aria-activedescendant (the active option, absent when none) and the accessible name "Search for movies here" (aria-labelledby the heading text). The popup is `<div role=listbox id=movie-search-listbox aria-label="Movie suggestions">` rendered only when open; options are role=option with ids movie-search-option-0..2 and aria-selected (true on the active one); their name is the movie title. A `role=status` polite live region announces "N results available" while open and "No results" when the user searched and nothing came back; empty otherwise. Keyboard (focus stays in the input): ArrowDown/ArrowUp move the active option and wrap (on a closed list with results they open it and activate first/last); Enter on an active option does what a click does (loads details, opens the dialog, hides the list; Enter with no active option does nothing); Esc closes and keeps the value (no-op when closed); Tab closes and moves on; typing resets the active option; mouse movement over an option makes it active; pressing inside the list does not blur the input. Click/tap outside (document `pointerdown`, capture, removed on unmount) and focus leaving close the popup; clicking the input still toggles it. Active option indicator: fill `--option-active-bg` plus 2px inset `--option-focus` ring (>= 3:1 on both fills, ACCESSIBILITY-COLORS.md). Step 4b: a zero-result search clears the options (no stale suggestions, popup closed, no active descendant, "No results"). Regression: e2e/a11y-autocomplete.spec.js, both modes, including axe (wcag2a/aa/21/22 + best-practice) on the open popup.

- BC-23 Home wallpaper pan (migration/movie-atlas step 4b, 2026-11-07, deliberate visual change, owner-requested). The wallpaper (collection.jpg, same image, white wash in light mode) is a `position: fixed` `body::before` layer at z-index -1 (not a body background and not `background-attachment: fixed`, which iOS Safari ignores), `pointer-events: none`, height 100vh with 100lvh where supported, out of flow. Its `transform` runs the CSS animation `wallpaper-pan` (48s linear infinite): zoom 1.3 and a window travelling a square (top-left, top-right, bottom-right, bottom-left, +-10%), `translate3d`/`scale3d`, `will-change: transform`, `backface-visibility` (with the -webkit- prefix). `prefers-reduced-motion: reduce` turns the animation off and shows the plain unzoomed photo. Without the animation (reduced motion, Playwright `animations: 'disabled'`) the layer equals the old static wallpaper. Contrast is measured on the static photo and the four extreme poses. Regression: e2e/background.spec.js (Chromium, WebKit desktop, WebKit iPhone) and the pose loop in e2e/a11y-contrast.spec.js.

## Windowed poster grid (migration/movie-atlas step 5, 2026-11-08)
- BC-24 Windowing. Only the tile rows near the viewport (viewport height plus 0.75 viewport above and below) are mounted; a fixed-height spacer (`.list-spacer`, aria-hidden, inline px height) above and below stands in for the others, so the grid has the height and every tile the position it would have with all tiles rendered (rows are measured from a real tile, tile CSS is unchanged). The scroll offset and viewport height come from the smooth-scrollbar instance (`offset.y`, `size.container.height`). Mounted tiles, `.poster[src]` images and DOM nodes stay bounded (about 60 tiles at 1280x800, 500 tiles = 25 pages never exceed 120). Tiles keep `id="<index>"`, `key=index` and the same markup; `.movieList-container` carries `data-total` (list length). Visible quirk-free effect: `document.querySelectorAll('.poster').length` is the MOUNTED count, not the list length. Note 2026-11-08 (Step 5b): the overscan is no longer a symmetric 0.75 viewport; it is 1.75 viewports ahead and 0.5 behind in the scroll direction, capped at 108 mounted tiles (the bounds above, the scroll height and the positions are unchanged; see BC-31).
- BC-25 Next page. One IntersectionObserver (root: the scrollbar `<section>`, no margin, so "sentinel visible" matches the old "last poster visible") watches a zero-height `.list-sentinel` after the grid. A scroll still starts the 600 ms debounce; when it fires and the sentinel is within the margin, `append()` is called once; the gate re-opens when the list length changes (or, for a failed/empty response, on a later scroll after 3 s). Result: pages 2..N are requested exactly once each, in order. No scroll, no request (also when the sentinel is already near the viewport on load); scrolling at the top of a long list requests nothing. The tablet quirk (BC-10) calls `append` through the Show More button and is unchanged.
  Note 2026-11-08 (Step 5b, owner decision): "No scroll, no request" no longer holds. The sentinel is evaluated against a margin of 3 viewport heights (px computed from the scrollbar container height, IntersectionObserver rootMargin plus a synchronous check), so on load a short list (and any list whose end is within 3 viewports) requests pages 2, 3.. on its own, once each and in order (BC-31); a scroll no longer starts a 600 ms debounce, and the 3 s re-arm is replaced by the failure backoff. Scrolling at the top of a long list (sentinel farther than 3 viewports) still requests nothing.
- BC-26 Back to the top. The list state is not touched by windowing, so scrolling to the bottom and back mounts the same tiles as the first load: same movies, order, `src`, no duplicates, no request.
- BC-27 No scroll jump. Appending a page, mounting and unmounting tiles never change the scroll offset or the position of a mounted tile (spacers keep the height; `overflow-anchor: none` on the grid and spacers).
- BC-28 No blank tile. Every tile that overlaps the viewport is mounted once scrolling stops; a tile is always the same size; `.poster` has a placeholder background (`--poster-placeholder`, both modes) until the image loads, and `decoding="async"`.
- BC-29 `.poster` has `cursor: pointer`.

## Prefetch and no empty tiles (migration/movie-atlas step 5b, 2026-11-08, owner decision)
- BC-31 While scrolling down (wheel, touch, keyboard, scrollbar drag) the viewport and the area just below it always hold real posters: never a blank placeholder tile, never a bare spacer, and never the end of the list inside the viewport while more pages remain (limit: a fling faster than the network, see below). Mechanics: (1) the sentinel (BC-25) triggers the next page when it is within 3 viewport heights of the viewport, no scroll or debounce needed; up to 2 page requests in flight, committed to the list strictly in page order by an ordered pipeline (`src/use-page-pipeline.ts`, the legacy `append` stays for Show More and BC-10); a page is requested once; on failure (network error, error body) all requests pause for 1 s, 2 s, 4 s .. 15 s and the failed page is requested again, later pages stay stashed (nothing skipped or duplicated); the last page (total_pages, or an empty page) stops requests; at most 8 pages in a row without a scroll; nothing is requested while a page-1 reload is in flight (the list would be replaced) or the list is not the route's category. (2) Windowing overscan is asymmetric: 1.75 viewports ahead and 0.5 behind in the scroll direction (kept in the last direction when idle), the visible rows are always mounted, the cap is 108 mounted tiles. (3) Posters just beyond the mounted window (1.5 viewports) and the predicted landing zone of a fling (offset plus per-frame delta / smooth-scrollbar damping) are fetched and decoded ahead with `new Image()` + `decode()` (6 at a time, at most 36 held, the queue is replaced on every change). BC-24 bounds, BC-26 (same tiles back at the top), BC-27, BC-28 and tile size/layout are unchanged. BC-10: the five auto "Show More" clicks keep exactly their requests (initial, nav click, five `page=2`); the prefetch is held back until they have changed the list, then continues the numbering from page 7. Tests: `e2e/scroll-prefetch.spec.js` (mocked latency: api 300-800 ms, posters 100-400 ms).
- BC-32 Page counter reset per category (Step 5c, owner decision 2026-11-08, supersedes the BC-05 quirk). When a page-1 load for a DIFFERENT category than the one loaded commits, the counter restarts at 2: each category requests `page=1` (the nav click, same sequence as before) then 2, 3, .. once each, in order, for Show More and the prefetch pipeline alike (single place: `usePagePipeline.reset(category, totalPages)`, called by `fetchData`). Reloading the SAME category (initial Popular load, then the Popular nav click) does not touch the counter, so BC-10 on the first load is exactly as before (initial, nav click, five `page=2`, then prefetch 7, 8..). A response that was requested for a category that has since been replaced (legacy `append`, or a pipeline page) never reaches the new list (generation / epoch guard), and of two page-1 loads only the latest click commits (an older, slower answer is dropped). BC-10 on later category switches (tablet 768-1024 px): the new list view still mounts and auto-clicks Show More 5 times, and those requests are the same as before: they use the render closure, i.e. the PREVIOUS category and its counter (five identical requests, no new-category data); their responses are discarded if page 1 of the new category has committed meanwhile, and otherwise are replaced by it; the counter is then reset to 2 and the prefetch continues the new category 2, 3, .. (not from 7). Test: `e2e/page-counter.spec.js`; `e2e/routing.spec.js` BC-05 now expects page 2 after a switch (was 4).
